## Повний шлях та перевірка позитивного рішення

Реальний приклад Сум: кандидат `a25952a45587fdc555fbbb43` → подія 20.09 у Зарічному районі → чинний `review_disposition` із явною приміткою про одну цивільну смерть від FPV → зіставлення первинного поліцейського URL / ID кандидата з `casualty:sumy:2026-09-20:fpv-double-strike-zarichnyi-apartment-entrance` → уже враховано 1 → дельта 0 → нового рядка немає. Виняток для такої старої людської верифікації дозволений тільки для результату +0 та перевіряється проти фактичного підтвердження у вхідній черзі.

Для нової додатної поправки на реальних даних прикладів немає. Щоб не підміняти їх вигаданим підтвердженням, позитивний ланцюг збережено окремо в `results/synthetic_positive_lineage.json` з явною позначкою **SYNTHETIC ONLY**:

- Два збережені тестові тексти прямо називають межі міста, дату/час, адресу, російську ракетну атаку й 2 цивільних загиблих. Один атрибутований ДСНС, другий поліції. Правила видобувають факти з текстів без готового `AUTO_READY` або ручних міток фактів.
- Місто + дата + адреса + час + вид атаки утворюють одну ідентичність події. Обидва посилання залишаються доказами.
- Подія після вересневої бази, у реєстрі її немає → пропозиція +2 у чинному форматі `REVISION_FIELDS`.
- У копії реєстру вже є +2; новий підтверджений повний підсумок 3 → пропозиція +1.
- Повтор із сумою вже внесених +2 та +1 → +0. Сценарій із попередніми ще не внесеними пропозиціями також резервує їхню дельту й не пропонує повторно +3.

## Правила та межі реалізації

Додано один модуль `casualty_auto_review.py` і підкоманду `auto-propose` чинного `review_casualty_candidates.py`. Оператор REVIEW/PROMOTE та його захист не змінені.

Ідентичність підтвердженої події включає місто, дату атаки, місце, часову ознаку та вид атаки. Заголовок, Google URL, кількість загиблих, дата жалоби/публікації та `trigger_episode_ids` до неї не входять. Перехідне злиття через схожі заголовки не виконується. Конфлікт прив'язки одного кандидата до двох подій блокує AUTO_READY.

Для нового позитивного рішення потрібні два різні документовані джерела походження доказів і два різні документи для кожного необхідного факту. Це навмисно суворий початковий контракт; його ефективність на широкій незалежній вибірці ще не виміряна. Різні домени, що переказують одне повідомлення, не утворюють два підтвердження. Старі зведення без встановленої незалежності залишаються однією сім'єю походження. Прапорець `strict_primary_control` не є доказовим полем.

Правила для збереженого повного тексту розпізнають лише дуже явні формулювання: точну дату атаки, час, адресу, межі міста, засіб атаки, цивільних загиблих і назване офіційне походження повідомлення. Звичайні варіанти мови поза цими шаблонами залишаються на перевірці. Обробка заперечення, непідтверджених чисел, некрологів і поранених блокує позитивне рішення. Повнотекстовий кеш у реальній черзі відсутній; код його не завантажує.

`cached_evidence.json` є разовим адаптером **готових** висновків діагностики та чинного підтвердження Сум. Це не результат автоматичного читання повних статей. Загальні правила видобування фактів з кешованого тексту перевірені синтетично; практичний відсоток автоматизації на нових повних текстах ще невідомий.

Порівняння з реєстром використовує event ID у примітці, посилання та кандидатів. Неприв'язаний старий запис того самого міста/дня, зміна ідентичності, від'ємна поправка або зниження числа блокують рішення. Для подій у межах історичної бази без подієвої деталізації повертається `BASELINE_EVENT_ALLOCATION_UNKNOWN`; відсутність місяця не перетворюється на нуль. Для майбутніх щодо вересневого знімка атак база не могла містити цю подію.
