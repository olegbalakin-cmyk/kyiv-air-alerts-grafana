# C2 fail-closed canonical persistence candidate (2026-10-27)

**Scope:** isolated research branch based on `site-prod@056668981b59194d95386eac4c236f569ffffe17`. The actual scheduled updater workflow lives on **main**, not on site-prod. This branch does **not** change main, site-prod or a production workflow; it does not connect to Neon. The `update-netlify-site.candidate.yml` below is a **non-executing release blueprint**, copied from `main@2d865aa3578af896893fc964406222f67416b2d7`, not an active workflow.

## Current failure and trace

The updater on main checks out site-prod and constructs the same-run 23-city canonical payload through `scripts/multicity_shadow_payload.py` (producer calls in `update_data.py`, `apply_ukrainealarm_bridge.py`, `add_sevastopol_exact.py`). After filling `dashboard_data.json`, it invokes `multicity_canonical_shadow.py` with the payload and `fail_open`. The shadow loads 23 keys, opens a PostgreSQL connection and calls `multicity_canonical_postgres.persist_canonical_episodes()`. The writer starts a transaction, checks existing episodes, inserts missing rows, finalizes an ingestion-run record and calls `connection.commit()`, or rolls back. The old wrapper could translate an exception into `status=failed` with process exit 0; its JSON `status=succeeded` also did not validate the writer's nested status and counts. The main workflow pushed `ukrainealarm_bridge.json` into site-prod **before** the Neon call and full 23-city QA; that early push could not be rolled back.

## Candidate changes / publication contract

- `kyiv-air-alerts-grafana/scripts/multicity_canonical_shadow.py`: require fail_closed for the enabled operation, never swallow DB/commit errors, return nonzero from CLI without leaking raw exception details, and require a consistent committed/exact-retry writer result before emitting a successful diagnostic.
- `kyiv-air-alerts-grafana/scripts/verify_multicity_canonical_receipt.py`: independent fail-closed diagnostic gate (23 cities, valid Git provenance, positive corpus, consistent counts, success policy and commit/exact-retry result). Disabled, failed, absent, malformed or contradictory receipts block publication.
- `research/c2_fail_closed_2026_10_27/update-netlify-site.candidate.yml`: future **main** updater blueprint; sets canonical failure_policy=fail_closed, gates downstream build on verified receipt, eliminates the early `Persist verified UkraineAlarm bridge checkpoint` push, revalidates the bridge against the current remote after every rebase and commits the bridge together with data at the final Git push. `PHASE1_DB_SHADOW_FAILURE_POLICY` remains unchanged.
- `kyiv-air-alerts-grafana/tests/test_multicity_c2_fail_closed.py` and `.github/workflows/c2-fail-closed-offline.yml`: disposable local PostgreSQL 18 integration tests with 23 synthetic city episodes, real commit and rollback, injected pre-/post-commit acknowledgement failures, exact retry idempotency, connection refusal, invalid receipts and static workflow-order assertions. The offline CI workflow has read-only repository permissions, no Neon secrets and no site-prod checkout/push.

## Limits and future release

The tests use a deliberately **reduced synthetic PostgreSQL schema** and no real Neon, current site-prod data, full production workflow execution, concurrency race or deployed Netlify read-back. A successful CI run proves only a **bounded offline C2 candidate**, not `C2=PASS`, Neon production cutover or a deployed fail-closed policy. In particular, commit acknowledgement from the driver is not an independent durable Neon read-back. Git push is not atomic with PostgreSQL COMMIT; a committed DB write followed by a failed Git push must remain retryable and not be reported as published.

A later **separately authorized** release must review/rebase the blueprint against then-current main, update the **main updater** and **site-prod script + verifier** together under an approved coordinated deployment, protect the scheduled collection window, and then prove a real scheduled Neon write/confirmation plus 23-city publication/read-back. Do not change Phase-1 shadow failure policy, WIP, casualty, historical/backfill or other persistence tracks through this candidate.
